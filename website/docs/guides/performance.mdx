# Performance

## What the library does

- **Native-driver animations.** Wheel 3D transforms, fades, month slides and sheet transitions run on the UI thread on iOS and Android.
- **Native drag for sheets.** On iOS and Android the sheet drag is a native `ScrollView` that snaps on the UI thread, so the sheet follows your finger even while JavaScript is blocked.
- **Virtualized lists.** Wheels and the emoji grid are `FlatList`s with `getItemLayout`, so only visible rows exist and scrolling never measures.
- **Memoized rows.** While a wheel scrolls, only the two rows whose selected state flips re-render. Calendar days and emoji cells are memoized too.
- **Lazy emoji data.** The 1,923-emoji table is parsed on first use and cached.
- **Formatter cache.** `Intl.DateTimeFormat` instances are cached per locale and options.

## What you can do

**Keep `items` / `options` stable.** Define them outside the component or `useMemo` them. New arrays every render make wheels re-normalize their items.

```tsx
// ✅ stable
const HOURS = Array.from({ length: 24 }, (_, i) => i);
function Example() {
  return <WheelPicker items={HOURS} … />;
}
```

**Memoize `theme` and `styles` objects**, especially on wheels:

```tsx
const theme = useMemo(() => ({ colors: { primary: brand } }), [brand]);
```

**Keep callbacks light.** `onValueChanging` fires on every row crossing; do haptics or cheap updates there, not network calls. Save in `onChange`.

**Keep `isDateDisabled` fast.** It runs for up to 42 days per render. Precompute a `Set` of `toDateKey`s.

**Mount sheets once.** Keep `<DatePickerSheet visible={open} … />` in the tree and toggle `visible`. It renders nothing while closed.

**Long select lists.** `SelectList` is virtualized. For thousands of options, give it a `listHeight` so the FlatList can window.

## Benchmarks

Animations that run on the UI thread keep moving when JavaScript is busy, for example while a screen renders a long list. To check that, we ran the same gesture on each component, ours and the most popular library for the same job, while the JS thread was blocked for 0, 50, 100 or 200 ms at a time (with one free frame between blocks).

Each cell is **frames per second · longest freeze** while the gesture runs: the frames in which the component's area changed on a screen recording, and the longest gap between two of them. Higher fps and a shorter freeze are better. 60 fps is the screen's limit; a freeze of about 17 ms is no dropped frame, 33 ms is one.

### What the numbers say

- **Gestures don't freeze under load.** Every drag and scroll runs on the UI thread, so blocking JavaScript for 200 ms at a time doesn't stop the gesture. Up to v0.28, the sheet drag ran in JavaScript and dropped to 7–10 fps at 200 ms. It now runs on the UI thread: on Android it beats `@gorhom/bottom-sheet` (60 fps against 56), and on iOS both hold 60 fps with shorter freezes for ours, all without Reanimated or Gesture Handler.
- **Wheels** match Quidone's wheel picker at 60 fps on both platforms (on iOS with shorter freezes for ours) and outpace `@react-native-picker/picker` on iOS. On Android our wheel drops one frame when the finger lifts and the row snaps.
- **Calendars** are even. The calendar's fps is lower than the others' because the month only moves for part of the measured window. `react-native-calendars` pages its months in a native scroll view that follows the finger; ours changes month when the finger lifts, then slides the new month in on the UI thread.
- **Emulators and simulators aren't phones.** Absolute numbers depend on the machine, and the screen recording itself costs frames. Compare rows from the same table, not across tables.

### Libraries we couldn't measure

On React Native 0.88 (Expo SDK 58), these libraries crash before they render, because they call `InteractionManager`, which React Native 0.88 no longer exports:

- `react-native-modal` 14.0.0-rc.1: `Cannot read property 'createInteractionHandle' of undefined` when the modal opens. See [Migrate from react-native-modal](../resources/migration/react-native-modal).
- `rn-emoji-keyboard` 1.7.0: `Cannot read property 'runAfterInteractions' of undefined` when the keyboard renders. See [Migrate from rn-emoji-keyboard](../resources/migration/emoji-keyboard).

`@react-native-picker/picker` is a dropdown on Android, not a wheel, so it's only in the iOS table.

### Run it yourself

The benchmark app lives in [`example/src/benchmark`](https://github.com/elik56a/react-native-pickers/tree/master/example/src/benchmark). Start it with `EXPO_PUBLIC_BENCHMARK=1 npx expo start --no-dev --minify`, pick a component and a JS load, then drag while recording the screen. The other libraries are dependencies of the example app only; the published package still has none. Expo SDK 58, React Native 0.88, Reanimated 4.7.1 and Gesture Handler 3.3.0 for the libraries that need them; JavaScript runs without dev mode in Expo Go.
